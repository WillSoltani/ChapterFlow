# ChapterFlow Bug Hunt — 2026-06-15

Whole-project bug hunt run as a multi-agent workflow. **36 confirmed** defects after adversarial verification. All 36 are filed as GitHub issues **#64–#99** (see each item).

## Method

- **Find** — 9 subsystem finder agents (auth/session, billing/Stripe, reader/content, user-data & repos, admin/metrics, referral-abuse-account, infra/lambda, pipeline scripts, frontend/React) + 3 `security-auditor` passes (access-control, injection/input, secrets/crypto). 12 agents, **57 candidate findings**.
- **Dedup** — merged overlapping reports → **51 canonical findings**.
- **Verify** — each finding judged by **3 independent adversarial skeptics** with distinct lenses (does-the-code-path-do-this / is-there-an-existing-guard / is-the-impact-reachable), each defaulting to *refuted* when unsure. A finding survives only if **≥2 of 3** independently confirmed it by reading the real code.
- **Result** — **36 confirmed**, **15 dropped**. (166 sub-agents total.)

## Critical (1)

### C1. Frontend stack ships the known prod-outage Function URL config (AWS_IAM + OAC + RESPONSE_STREAM)

- **Where:** [infra/lib/chapterflow-frontend-stack.ts:416-419, 607-619](infra/lib/chapterflow-frontend-stack.ts#L416) · **Issue:** [#64](https://github.com/WillSoltani/ChapterFlow/issues/64)
- **Category:** config  ·  **Confidence:** 3/3 verifiers  ·  **Reported by:** infra-lambda
- **Impact:** The server/image Function URLs are created with authType AWS_IAM + InvokeMode RESPONSE_STREAM and fronted by FunctionUrlOrigin.withOriginAccessControl. This is the exact combination that 403'd every route in production (documented incident funcurl-oac-deploy-403): AWS_IAM + OAC rejects RESPONSE_STREAM origin requests at runtime, and cdk synth cannot catch it. main was reverted to authType NONE + plain FunctionUrlOrigin (PR #61), but this audit branch still carries the broken config. Deploying this frontend stack reproduces a full site outage (every page/API → 403).
- **Repro:** cdk deploy ChapterFlowFrontend from this branch, then hit any route through CloudFront — origin returns 403 for all paths (synth/diff pass, runtime fails).
- **Fix:** Set both addFunctionUrl calls to authType: lambda.FunctionUrlAuthType.NONE and use origins.FunctionUrlOrigin(...) (no OAC), matching main.

## High (6)

### H1. Free-unlock anti-fraud trusts leftmost (client-controlled) X-Forwarded-For, fully bypassable

- **Where:** [app/app/api/book/_lib/abuse.ts:48-62](app/app/api/book/_lib/abuse.ts#L48) · **Issue:** [#65](https://github.com/WillSoltani/ChapterFlow/issues/65)
- **Category:** authz  ·  **Confidence:** 3/3 verifiers  ·  **Reported by:** referral-abuse-account, sec-injection-input, sec-secrets-crypto
- **Impact:** readIp() takes forwarded.split(',')[0] — the LEFTMOST XFF entry, which is supplied by the client and appended-to (not overwritten) by CloudFront; the trustworthy cloudfront-viewer-address header is only consulted AFTER the spoofable XFF. buildSignals() derives the network/network_ua fraud fingerprints from this IP, and assertFreeUnlockAllowed() (ensure-book-started.ts:200, abuse.ts:217-262) throws 403/429 based on network velocity over those fingerprints. By rotating a fake X-Forwarded-For per request, an attacker mints a fresh network bucket every time, defeating network_velocity / network_user_agent_velocity / stacked_shared_signals and the email-verification gate, farming free unlocks (and the referral/IP economy that buys Pro). app/api/book-requests/route.ts:99-121 has the correct trusted-rightmost pattern; this file was not migrated.
- **Repro:** Send book-start requests each with a different spoofed `X-Forwarded-For: <random-ip>`; every request lands in a new coarse-network fingerprint so network-velocity never trips, granting unlimited free unlocks.
- **Fix:** Read the Nth-from-right XFF entry (RATE_LIMIT_TRUSTED_PROXY_HOPS) or cloudfront-viewer-address first, mirroring readClientIp in book-requests/route.ts, instead of split(',')[0].

### H2. Gift-code claim overwrites a longer-lived license/flow_points Pro grant, silently shortening or destroying paid access

- **Where:** [app/app/api/book/me/gifts/[code]/claim/route.ts:89-107](app/app/api/book/me/gifts/[code]/claim/route.ts#L89) · **Issue:** [#66](https://github.com/WillSoltani/ChapterFlow/issues/66)
- **Category:** logic  ·  **Confidence:** 3/3 verifiers  ·  **Reported by:** billing-stripe, user-data-repos
- **Impact:** The claim's entitlement Update guard is only `attribute_not_exists(proSource) OR proSource <> :stripeSource`, so it protects Stripe subscribers but NOT license/flow_points/gift users. It unconditionally SETs proSource='gift_code' and currentPeriodEnd = now+7d. A user with an active 12-month license (or a 30-day flow_points pass with 23 days left) who claims a 7-day gift has their entitlement flipped to gift_code; getUserEntitlement (repo.ts:693-700) then derives expiry from currentPeriodEnd for gift_code, ignoring the stale licenseExpiresAt — so the user loses up to ~11 months of paid/redeemed access after 7 days. The same unconditional currentPeriodEnd overwrite shortens any longer non-stripe grant (and the identical pattern exists in redeemFlowPointsReward in flow-points-repo.ts ~666-687 where a later/shorter pro_pass overwrites a longer active one).
- **Repro:** User redeems a license key (proSource='license', licenseExpiresAt = +12mo), then later claims any gift code. proSource becomes 'gift_code', currentPeriodEnd = +7d; after 7 days the license is no longer honored and Pro is lost. (Or redeem a 30-day pro_pass, then claim a 7-day gift; currentPeriodEnd drops from ~30d to 7d.)
- **Fix:** Only apply the gift if it extends access: condition like `attribute_not_exists(currentPeriodEnd) OR currentPeriodEnd < :expires`, refuse downgrading a non-stripe grant, and set currentPeriodEnd to max(existing, new). Apply the same max-expiry guard in redeemFlowPointsReward.

### H3. Quiz pass / chapter-unlock bypass via index-only (legacy-path) submission

- **Where:** [app/app/api/book/me/quiz/[bookId]/[chapterNumber]/submit/route.ts:331-365](app/app/api/book/me/quiz/[bookId]/[chapterNumber]/submit/route.ts#L331) · **Issue:** [#67](https://github.com/WillSoltani/ChapterFlow/issues/67)
- **Category:** authz  ·  **Confidence:** 3/3 verifiers  ·  **Reported by:** reader-content
- **Impact:** When NO response carries a selectedChoiceId (the client sends only selectedIndex), grading falls to the legacy scoreQuizResponsesByQuestionId, whose total is responses.length rather than the chapter's required question count. The strict path (gradeQuizAttemptQuestions) enforces questionResults.length === questions.length, but the legacy path has no minimum-coverage check. A user can submit a SINGLE correct index-only answer (the correct index is already exposed to the client via the documented correctChoiceId field in the quiz GET) and score 100%, passing the quiz, advancing unlockedThroughChapterNumber, completing the book, and farming quiz-pass/loop/book-complete Insight Points in one request, so the per-attempt cooldown/rate limit never engages.
- **Repro:** GET the quiz to read q1's correct index, then POST /me/quiz/{bookId}/{chapterNumber}/submit with body {responses:[{questionId:'q1',selectedIndex:<correct>}], attemptNumber:1}. scorePercent=100, passed=true, next chapter unlocks despite answering 1 of N questions.
- **Fix:** Require responses.length === attemptQuestions.length (the maxQuestions-sliced set) before grading, and have the legacy path compute scorePercent over the full attempt question set, not responses.length.

### H4. Gift purchase deducts Insight Points then creates the gift code in a separate non-atomic write — IP lost if the second write fails

- **Where:** [app/app/api/book/me/shop/route.ts:107-174](app/app/api/book/me/shop/route.ts#L107) · **Issue:** [#68](https://github.com/WillSoltani/ChapterFlow/issues/68)
- **Category:** data-corruption  ·  **Confidence:** 3/3 verifiers  ·  **Reported by:** billing-stripe, sec-secrets-crypto
- **Impact:** The IP deduction + ledger entry run in one TransactWriteCommand (lines 108-148), but the gift-code record is persisted by a SEPARATE PutCommand afterward (lines 158-174). If that PutCommand fails (DynamoDB error, throttling, Lambda kill between awaits, or a UUID-collision ConditionExpression rejection), the user has already irreversibly spent their Insight Points but receives no gift code and gets no refund — the response throws and the points are gone; a retry charges them again. The personalization-item branch right below puts deduction+inventory+ledger in ONE transaction, showing the intended atomicity the gift branch lacks.
- **Repro:** User buys 'Gift a Friend'; the IP-deduction transaction commits; the subsequent gift-code PutCommand throws (e.g. transient ProvisionedThroughputExceeded). User's balance is debited the IP cost with no gift code returned.
- **Fix:** Move the gift-code Put into the same TransactWriteCommand as the IP deduction/ledger so both commit or neither does.

### M1. recordEventChapter is a non-atomic read-modify-write (lost updates to event progress)

- **Where:** [app/app/api/book/_lib/events-repo.ts:78-131](app/app/api/book/_lib/events-repo.ts#L78) · **Issue:** [#71](https://github.com/WillSoltani/ChapterFlow/issues/71)

### M2. Location resolver uses leftmost X-Forwarded-For (spoofable client IP)

- **Where:** [app/app/api/book/_lib/location.ts:27-44](app/app/api/book/_lib/location.ts#L27) · **Issue:** [#72](https://github.com/WillSoltani/ChapterFlow/issues/72)

### M3. markNotificationRead upserts phantom notification rows (no existence guard)

### M10. Login redirect host derived from unvalidated x-forwarded-host (open redirect / phishing)

- **Where:** [middleware.ts:12-26, 81-94](middleware.ts#L12) · **Issue:** [#80](https://github.com/WillSoltani/ChapterFlow/issues/80)
- **Category:** authz  ·  **Confidence:** 2/3 verifiers  ·  **Reported by:** auth-session, sec-injection-input
- **Impact:** resolveRequestOrigin() builds the /auth/login redirect base purely from the client-supplied x-forwarded-host (or host) header with no allowlist and, unlike the parallel resolvePublicOrigin() in app/app/_lib/server-origin.ts, it never prefers the trusted APP_BASE_URL/CHAPTERFLOW_APP_BASE_URL. ### M12. License-key seeding does both PutCommands in Promise.all with no rollback on partial failure

- **Where:** [scripts/book/generate-license-keys.mjs:106-143](scripts/book/generate-license-keys.mjs#L106) · **Issue:** [#82](https://github.com/WillSoltani/ChapterFlow/issues/82)
