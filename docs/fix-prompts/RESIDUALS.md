## Pre-merge review fixes (PR #44, 2026-06-14)
A pre-merge code review of PR #44 surfaced findings beyond the audit catalog. Fixed in code on this branch (each authored on a `review/<ID>` branch, merged only after the integrated gate passed: `tsc` clean · 117 tests · `next build` ✓):

- **B1 (BLOCKER — FIXED)** — `checkReferralEscalation` defaulted `highestMilestoneReached` to 0, so newly wiring the (previously dead) escalation path live would lump-grant every tier ≤ an existing inviter's lifetime `activatedInvites` — up to 4,600 IP + 3 cosmetics — on their first post-deploy activation (the annual cap can't stop it: `rollingYearActivations` also defaults to 0). Now seeds from `highestPassedTier(activatedInvites - 1)` (the tier reached BEFORE this activation), so only tiers crossed AFTER go-live pay out, and a new inviter still earns each tier as they cross it. **No backfill/migration needed** — the seed is purely runtime. NOTE: the review's literal `highestPassedTier(activatedInvites)` was deliberately NOT used — it would permanently deny every new inviter all tiers (on the crossing activation `highestSettled == seed`, so the field never persists and the seed re-applies forever). Unit tests added (`referral-escalation-core.test.ts`).
- **C1 (CONCERN — FIXED)** — `reserveBookEntitlement` now self-heals a NULL `unlockedBookIds` row (corrupted while `convertEmptyValues:true` was deployed): on the `ADD`'s `ValidationException` it conditionally `REMOVE`s the NULL attribute (a NULL set ≡ empty ≡ no real unlocks → no data loss) and retries the reserve once. This replaces the manual deploy-day backfill the review flagged — **no owner action required**.
- **C2 (CONCERN — FIXED)** — `/auth/refresh` rate-limiter keys on the raw `cf_device` cookie with a genuine IP fallback (was keying on `getOrCreateDeviceId`, which mints a fresh UUID per cookieless request → unthrottleable, with the documented IP fallback dead).
- **C3 (CONCERN — FIXED)** — beacon consent cache stores ONLY the opt-OUT direction, so disabling analytics takes effect on the very next beacon (was: up to 60s of stale opt-in storage after opt-out, with no PATCH-route invalidation hook).
- **N2 (nit — FIXED)** — removed the dead `export const maxDuration = 60` from the admin economy route (OpenNext bundles one ServerFn at a fixed 30s CDK timeout and ignores per-route `maxDuration`).
- **N3 (nit — FIXED)** — Segment Builder warns at the real 500-recipient synchronous cap via a shared `MAX_SYNC_RECIPIENTS` constant, instead of the stale "5,000 per send" label (501–5000-user segments previously got no warning then hit a 400).
